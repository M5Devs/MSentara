## The two real bugs (both silent in Release)

1. **Missing `sg_commit()`.** sokol_gfx defers resource creation and
   buffer/image updates to `sg_commit()`. Without it the UI still drew (pure
   ImGui draw-list geometry) but the offscreen 3D viewport sampled a black
   texture — the Image rendered, just empty. Fix: call `sg_commit()` once at
   the end of `frame_cb()`, after the swapchain pass ends. `sokol_imgui.h`
   never calls it itself (grep: 0 hits).

2. **MSAA sample-count mismatch on the offscreen target.** `sg_image_desc`
   render-target images inherit `sg_desc.environment.defaults.sample_count`
   (= the swapchain MSAA count, 4 here) when left at 0. The pipelines were
   built at 1, so Debug builds panicked with
   `VALIDATE_APIP_ATTACHMENT_SAMPLE_COUNT`. Fix: set `sample_count = 1`
   explicitly on the color + depth images. Pipelines also hardcode
   `desc.sample_count = 1` to match.

Both were invisible in Release because `SOKOL_ASSERT`/validation is compiled
out. **Always reproduce sokol problems in a Debug build** — the validation
layer names the exact log item.

## Verification method that worked (headless)

No GPU in the container, but software rendering works:
`Xvfb :77 -screen 0 1600x900x24` + `LIBGL_ALWAYS_SOFTWARE=1
GALLIUM_DRIVER=llvmpipe MESA_GL_VERSION_OVERRIDE=4.5
MESA_GLSL_VERSION_OVERRIDE=450`, then `import -window root out.png` to capture.
Confirm content by counting distinct colours / non-background pixels per region
rather than eyeballing. A `MSENTARA_FRAME_LIMIT=<n>` env var makes the app
`sapp_request_quit()` so headless runs terminate on their own.

The only stderr noise that is expected here is
`LINUX_X11_QUERY_SYSTEM_DPI_FAILED` (no `Xft.dpi` resource in Xvfb).

## Other gotchas hit

- sokol_app's X11 backend needs `X11` plus `Xcursor`/`Xi`/`Xext` linked
  explicitly on Linux; without them the link fails with
  `undefined reference to symbol 'XConvertSelection'`.
- `glm::perspective` puts the -1 in **`m[2][3]`**, not `m[3][2]`. A test
  asserting `[3][2]` was wrong, not the camera code.
- ImGuizmo must be included *after* `imgui.h` (it uses ImGui types).
- `ImGuizmo::IsOver()`/`IsUsing()` is the correct input arbiter in the
  viewport, **not** `io.WantCaptureMouse` — the viewport is itself an ImGui
  window, so `WantCaptureMouse` is always true inside it and would disable
  navigation entirely.

## Build facts

- CMake 3.20+, deps via `FetchContent` (sokol, imgui `docking`, ImGuizmo, glm
  1.0.1). ImGuizmo's own CMakeLists is bypassed with a non-existent
  `SOURCE_SUBDIR` so only its sources are populated.
- Our code compiles clean under `-Wall -Wextra -Wpedantic -Wshadow
  -Wconversion -Wsign-conversion -Wdouble-promotion -Wformat=2`; only
  third-party glm emits sign-conversion warnings (it is a SYSTEM include).
- `cmake -S . -B build -G Ninja -DCMAKE_BUILD_TYPE=Release && cmake --build
  build` → clean. `ctest --test-dir build --output-on-failure` → 5/5 pass.
- Emscripten path is wired (`MSENTARA_WEB`, GLES3, `-sUSE_WEBGL2=1`) but
  **unverified** — no `emcc` in this container.

- **Three real bugs found by the tests** (all fixed):
  1. `resolve_order` hung forever on a cyclic parent chain.
  2. test_deep_hierarchy passed *relative* positions to `add_bone`, which
     takes *model-space* ones — expectation was wrong, not the code.
  3. The synthetic PMX wrote BDEF2's weight as a float and put all four edge
     scales after the vertices; both are wrong (weight is one byte, edge
     scale is per-vertex). Parser updated to the correct spec; test fixed.

  `MSentara --pmx <path>` (or `MSENTARA_PMX=`) loads it. Headless Xvfb run
  printed `loaded '…' (8 vertices, 2 bones, 1 materials)` and a screenshot
  showed the cel-shaded cube (`#E68066`) plus the gizmo axes.

  the container OOMs under parallel compilation.
